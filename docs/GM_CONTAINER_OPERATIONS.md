# 角色容量管理

角色资料的“容量管理”页签提供主背包、装扮栏和个人仓库扩容。可分别选择目标档位，也可一次扩至最大；提交前展示各项前后值，完成后进入分页扩容流水。

| 容器 | 页面数值含义 | 当前协议支持的档位 |
| --- | --- | --- |
| 主背包 | 扩展格数 | 0、8、16、24 |
| 装扮栏 | 扩展格数 | 0、7、14、21、28、35、42、49、56 |
| 个人仓库 | 总格数 | 8～200，每档增加 16 |

容量来自游戏 `CharacterContainerState` 的持久字段，进入游戏及物品列表刷新通过当前客户端 op13 头部读取。已有角色必须存在有效容器记录；缺失时页面显示初始化提示。扩容保持当前容量或提高档位，缩容需要另行实现超出容量物品的迁移流程。

## 接口

| 方法与路径 | 内容 |
| --- | --- |
| `GET /api/v1/characters/{id}/containers` | 是否初始化、当前值、可用档位和版本 |
| `POST /api/v1/characters/{id}/container-operations/preview` | 一至三项扩容的签名预览 |
| `POST /api/v1/characters/{id}/container-operations` | 提交原预览及请求编号，返回永久回执 |
| `GET /api/v1/characters/{id}/container-operations?limit=10&cursor=...` | 分页扩容流水 |

```json
{
  "accountId": "example:1",
  "targets": {"main": 8, "avatars": 7, "warehouse": 24},
  "revision": "<查询返回的版本>",
  "reason": "活动扩容"
}
```

预览返回 `receipt` 和十分钟有效的 `planToken`。提交在原请求中加入 `planToken`，并提供 `Idempotency-Key`；两个 POST 均校验登录会话和 CSRF。签名绑定完整内容、角色、归属及操作者。回执包括各项前后值、原因、操作人、时间和请求编号。

页面只在打开、显式刷新及翻页时查询。响应丢失后刷新页面，可以沿用原编号取得回执。已提交请求的恢复不依赖当前容器记录或游戏在线状态接口。

## 数据与事务

查询在只读一致性事务内读取角色归属和所需容量字段：三项容量、两个账号金库兼容字段及管理版本。每个设置值最多 128 字节，其他设置和物品存档不进入内存。

提交按角色行→容器设置行及相关值的顺序加锁，检查角色归属、删除状态、版本和档位。只保存选中容量字段、设置更新时间和 `gm_container_sequence_v1`；账号金库、商城扩容历史、来源及其他设置保持。回执写入 `container_management_operations`，按角色分片，与按设置 scope 分片的容量变更共用一个数据库事务。

角色上线状态在写入前后检查，容量和回执保存失败全部回滚。同编号相同请求返回原回执，同编号不同内容或旧版本返回冲突。管理回执表由显式安装命令创建，服务启动检查。

游戏端跨进程编辑锁继续作为上线前置项，用于覆盖在线采样后的登录竞争。原生客户端重新进场和仓库打开的展示验收列入第五阶段。

## 关联功能

账号金库开通、扩容与金币已接账号事务，见 [账号金库操作](GM_VAULT_OPERATIONS.md)。金币携带阶段、特殊装备槽和副本权限继续按所属领域规则接入。

战斗属性和负重在当前游戏选角时由 PVF 重新计算并写回。持久编辑需要游戏侧支持明确的属性覆写策略及取消覆写、PVF 升级与等级变化的行为，不能把普通属性列写入计为持久编辑完成。此依赖列入 GM-05/GM-07。

## 验证

- 一次性 MariaDB 单／双分片：有界查询、三项原子扩容、字段保留、预览零写、缺失记录、非法/缩容档位、并发重放与冲突、保存/回执失败及后置在线变化回滚、签名/CSRF、分页隔离和当前记录损坏后的回执恢复。
- `scripts/verify_gateway_containers.py`：实际网关页面、多项预览、刷新后重试、扩至最大、另一管理员修改后的冲突、物品及点券保持、角色/账号隔离、未初始化提示、深浅主题、390px和静置零请求。
