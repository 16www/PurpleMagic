# 福利规则的 PVF 换版

在“邮件与福利”的参数福利规则中选择“核对 PVF”，查看原版本与当前版本的物品名称、耐久、强化/增幅/锻造等参数。完整 PVF 摘要、单项脚本摘要和物品定义放在展开详情中。物品缺失或新版本不支持原有选项时，返回具体原因。

确认后，原规则继续使用同一编号、发放范围、邮件内容、金币、物品编号/数量和选项。未投递对象使用当前定义；已投递对象保留实际附件与时间。已保存的待发任务在下一批执行时采用已确认的规则版本，名单和投递进度继续保留。

相同 PVF 只展示核对结果。“核对历史”按页查看每次确认的前后版本、物品定义、时间和管理凭据标识。浏览器保存待确认请求，响应丢失后可刷新并“恢复确认”。提交成功后的恢复读取永久回执，当前 PVF 不可用或预览已过期时也能读回。

## 接口

| 方法与路径 | 行为 |
| --- | --- |
| `POST /api/v1/benefits/{id}/pvf-preview` | 请求体 `{}`；返回前后定义、`canApply` 和签名 `command` |
| `POST /api/v1/benefits/{id}/pvf-apply` | 原样提交 `command`，增加 `confirm:true`；返回核对回执 |
| `GET /api/v1/benefits/{id}/pvf-history` | `limit`、`cursor` 分页，游标绑定规则和页大小 |

两个 POST 都要求管理会话、CSRF 和同一个 `Idempotency-Key`。签名有效期10分钟，绑定规则编号/修订、新 PVF 摘要、完整投影摘要和请求编号。首次提交重新读取规则和当前定义；任一项变化返回冲突。同请求编号改内容返回 `idempotency_conflict`。记录已经提交时，先恢复原回执再处理预览时效。

## 持久化与并发

首次确认把原始静态附件和 PVF 摘要保存为不可变 `receiptBasis`。后续版本仍用这组字段计算历史发放指纹，规则的其余奖励内容保持。新投递回执增加实际 `pvfChecksum`；旧回执没有这个字段时保留原证据，不补写历史版本。

核对事务锁定规则，和手动批次、自动新角色投递的共享规则锁协调。已开始的批次完成后才更新定义；规则更新及核对回执同事务提交。任务采用新定义前，再比较不可变奖励和原始回执基础。

`<账号表>_benefit_pvf_ops` 保存独立核对历史，以规则编号和递增序号索引分页。升级使用现有 `--init-management-schema` 初始化新表；正常启动只检查。规则表、任务表、核对历史及账号永久回执一同纳入备份。

新建参数规则记录单项已解码脚本的 SHA256 和必要定义字段。旧规则没有单项摘要时，页面显示“历史单项脚本摘要未记录”，并比较已有静态参数。整个 PVF 的完整摘要仍决定索引代次；单项摘要不代表其他共享配置未变化。

此流程适用于带 `reward.deliveryPlan` 的参数福利。旧静态规则保持原有契约；普通单次邮件仍绑定首次预览的 PVF 和已固定实例。

## 验证入口

```text
python gateway/scripts/test_mysql.py --benefit-pvf-browser-script scripts/verify_gateway_benefit_pvf.py
```

一次性单/双分片数据库验证两种发放范围、连续换版、已删邮件的回执恢复、旧待发作业继续、自动/手动去重、历史写入失败回滚及进行中投递锁。签名篡改/过期、规则/PVF/投影变化、缺失物品和不支持参数均有拒绝场景。浏览器使用真实 HTTP 和隔离数据库验证差异展示、响应丢失恢复、历史、手机主题与空闲零请求。
